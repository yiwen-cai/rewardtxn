## 剩余差距（每步 R 约比 A 多 3.5–5 s）
- **B2 仍在关键路径上**：每步 finalize 等待 1.3–2.5 s，加上 join hasher 约 1.7–2.0 s。
  - 第 k 代的 DCP 写盘约 11 s，第 k+1 步从取批到保存只有约 10–12 s，写盘经常还没完。
  - hasher 要等 writer 退出后才开始对分片做 prehash（约 2.1–2.4 s），这一段因此也落在 B2 上。
- **训练段**：`batch_taken→optimizer` R 3.6–3.9 s，A 2.5 s（校验与争用）。
- **rollout I/O 线程**：10 步 CPU 31–37 s，flock 等待约 19 s；R 与 A 的每步等批时间已接近（5.0–6.6 s 对 6.5–6.8 s）。
- A 的保存段约 9 s，含共用观测器的全量哈希（推断）。两臂比率带着这一点解读。A 的等批时间在两次门控之间从 0.85 s 变到 6.5 s，跨 run 波动很大。

## 可选的后续方向（需用户决定，未实施）
1. **接受当前结果**：端到端墙钟 R/A 为 1.02–1.06，训练循环约 1.25，恢复功能完整。
2. **把 B2 进一步移出关键路径**：例如 lag=2（允许两个未决代），或者 B2 只做非阻塞 finalize、未完成就推迟到下一步。代价是状态协议更复杂，RPO 可能再加一步。
3. **在写盘时流式计算分片摘要**：给 fork 出的 DCP writer 打补丁，消除 join 等待（约 2 s/步）。
4. **削减 rollout I/O 线程的 CPU**：合并每条样本的 `_io` 调用。
