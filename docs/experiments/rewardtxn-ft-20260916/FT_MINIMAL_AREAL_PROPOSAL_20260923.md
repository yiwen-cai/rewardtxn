# RewardTxn × AReaL 最小容错补充实验提案

日期：2026-09-23；存储修订：2026-09-24。状态：**设计及存储修订经独立评审通过，尚非正式 freeze；正式样本仍为 0。** 本文拟取代 FT-v1 的后续执行范围；既有 FT-v1 文档、审计摘要和 30 步门控判定保持原样。按用户要求，旧 FT1 原始试跑证据已清理，详见 [清理记录](FT1_RAW_EVIDENCE_CLEANUP_20260924.json)；旧检查点现不能在本机重新加载复验，后续结论必须依靠新 pilot 和新正式 run 的证据。

## 1. 论文主张与比较边界

只研究一个可直接运行的已发表系统：固定 AReaL 源码加两臂共用的严格评分/launcher 工程补丁（A），以及相同底座增加完整 RewardTxn 的版本（A+R）。主张限定为：**在单机异步 RLVR 中，trainer 完成一次 optimizer 更新、对应 checkpoint 尚未保存时崩溃，A+R 能否安全复用该次中断更新已经完成的训练输入，而 A 使用原生恢复策略安全丢弃并补采。** 两臂最终都必须完成相同数量的正确持久更新；训练轨迹和使用的具体样本可以不同。整 run 耗时、GPU·小时和正常路径开销与复用收益一起报告，不预设更快或总体更省资源。

AReaL 是 [NeurIPS 2025 已发表异步 RL 系统](https://papers.neurips.cc/paper_files/paper/2025/hash/33c00862bfa29ac72ecf630a41e19352-Abstract-Conference.html)，其 [RecoverHandler 文档](https://areal-ai.io/AReaL/en/reference/checkpointing.html)说明了完整训练状态恢复。本地源码基线是 `third_party/areal` 的 `b83d1f40196e5bd7d9f83092563443561870d550`，带尚未提交的共用补丁；正式报告须保存这些补丁的 diff/hash，并以**本地固定版本实际代码**说明旧 SPMD 恢复语义，不能用官网当前版本的 `LATEST` 实现替代。对照的原生恢复、完整 checkpoint、组检查与严格评分重试均保持开启。

[RobustRL（OSDI 2026）](https://www.usenix.org/conference/osdi26/presentation/chen-zhenqian)研究角色级隔离及机器故障，[ByteCheckpoint（NSDI 2025）](https://www.usenix.org/conference/nsdi25/presentation/wan-borui)是 checkpoint 组件。本轮均不实测；论文不得声称优于它们，亦不得把本实验推广到多机、长期或任意异步写入窗口。这是现有论文的**窄范围容错补充**，不是整篇系统论文的完整实验集。

## 2. 独立评审核对出的设计更正

- 原提案把 F4 评分 child 故障设为主比较，并用“已生成 token 保留率”衡量收益；这不成立。共用 `strict_reward.evaluate` 对同一输入只重启本次评分子进程，父进程仍持有回答；F4 s417 的 A 已 `same_input_native_score_retry_succeeded` 且目标组最终保留。A 的回答保留率预计已达上限，不能关闭 A 的原生重试制造优势。F4 旧 pilot 只作为功能背景，不再增加正式 F4 run。
- F2 更对应 RewardTxn 的中断工作复用。旧审计摘要记录 A s419-r4 的四个被杀目标组全部安全丢弃、最终状态正确加载；R s419-r1 的被杀批次 32 条 tokens/versions/masks/rewards 在恢复后精确重放。两次试跑**并非同冻结正式配对**，原始证据已按用户要求清理，只提供历史设计线索；新版同条件 pilot 须重新证实切点、恢复与来源链。
- 9 月 23 日新版 30 步 F2 门控仍是**不通过**：R=2739.55 s、每步增长约 1.57 s、缺最终状态。新方案改为 10 步早期一次故障，仅收窄论文结论；不能把旧失败改判通过，也不能宣称长任务扩展性。

## 3. 固定的最小矩阵与预算

两臂均用 Qwen2.5-0.5B-Instruct、单训练 rank＋3 推理实例、4 张 H100、K=8、U=4、真实评分、同频率异步完整 DCP 和同一 launcher 重试策略。F2 切点明确定义为：**第 2 次成功 optimizer 更新之后，先等待前一代异步 checkpoint 完整，随后在这次更新的保存开始之前 SIGKILL trainer**。这个两臂共用的主动 drain 属于实验条件，计入全 run 成本；不代表未完成前代写入或任意异步时刻的恢复。每 run 从同一基座开始，最终目标为 10 次有效持久更新。

| 用途 | 配对 | GPU run | 论文用途 |
|---|---:|---:|---|
| F2 trainer 中断 | 10 | 20 | **唯一正式故障主比较**；固定 seed 成对、顺序均衡 |
| 无故障 | 3 | 6 | 同版本 A/R 正常路径成本；描述性，不与故障 run 相减归因 |
| 合计 | **13** | **26** | 比 HANDOFF 中拟做的 80 次 30 步 run 少 67.5% 的 run，单 run 目标步数也缩短 |

正式前各做 **1 对 F2、1 对无故障**同版本 pilot（4 run，不入正式分母），确认新版 10 步完成、故障命中、执行来源关联、空间与超时。若 pilot 失败，先修实现或观测，重新 freeze；不挑成功 seed 组成正式配对。正式 10 个 seed、顺序、窗口和技术无效最多一次同 seed 补做规则均须运行前固定。有效命中后的安全停止、超时与来源不明全数保留；若正式 pair 无法判定，不宣称总体统计优势。

旧版 10 步实测 F2 一对约 3.20 GPU·小时、无故障一对约 2.53 GPU·小时，故 26 次正式训练约 **40 GPU·小时**；4 次 pilot 另约 6 GPU·小时，尚未计入单 GPU 加载验收、补做及新版性能变化。GPU 用量不是授权或预留，须以新版 pilot 重估。现有无故障入口设 `retries=0`、故障入口设 `retries=1`，所以无故障数据只用于 A/R 同配置正常路径比较；不能相减得出故障净开销。

## 4. 预定结果与安全判定

**主效果（每 run 二值）**：故障前进入被杀 optimizer 更新的 4 个完整组、32 条原始回答与评分，是否在恢复后以**同一执行来源**进入最终保留训练状态。只有 32/32 均被真实复用并持久提交才记 1；安全丢弃、部分复用、同文本重新生成均记 0，部分复用量另报告。A 的 `safe_discard` 是有效且安全的基线结果，不因目标组没被保留而剔除。两臂以各自真实被杀批次为分母，分别记录原始回答 token、恢复后额外生成 token、verifier 调用和 GPU 成本。此指标回答“保留中断工作”，**不是训练质量或 RTO**。

**安全门槛**：实际命中同类 trainer 进程与上述切点；最终 10 次有效更新均对应完整 K 组和正确 reward；无重复保留更新；最终模型、optimizer、scheduler、RNG、数据游标经新进程加载一致。A 可以安全丢弃目标组后补采，R 可以重放未提交的物理 optimizer 更新；两者均不得把同一逻辑更新重复留在状态链。R 若有有效命中的 `invalid_commit`，本版本不能宣称安全通过。技术无效、超时和 `unverifiable` 均列入 10 对登记表及原因，不能从分母静默删去。

**统计与表述**：逐对列出 A/R 的二值复用结果、安全分类、原始/重做 token、完整 run 墙钟与 GPU·小时。对 10 对可判定且安全的正式样本，用双侧精确 McNemar 检验配对复用差异，预设阈值 0.05；同时报告双方比例各自的精确 95% 区间，不把 32 条样本或同 run 更新当独立重复。只有 10 对均可判定且安全、R 复用比例高于 A、双侧精确 `p<0.05` 时，才宣称该配置下的复用优势；反向显著也如实报告。若未达到条件，仅报告观察值及不确定性，不追加 seed 追显著性。10 对只能支持该单机短任务条件下的强、一致效果，不能证明低故障率或普适性。

**RTO**退出主检验：A 正确丢弃目标工作时，本次目标没有“首次恢复提交”时间，不能给它虚构无限 RTO 或与 R 的 commit 时间相除。可描述故障到下一有效更新的时间，但必须注明它不等于原始目标工作恢复；任何“恢复更快”措辞需另有同口径实验。

## 5. 最少实现工作与停跑条件

1. **先冻结范围与版本**：保留旧 FT-v1 文档、审计摘要及原判定，不恢复已清理的旧原始证据；另写本轮 freeze，包含 AReaL 固定 commit＋两臂共用补丁、R diff、镜像、数据、配置、故障 schedule、seed、有效 argv/GPU UUID、统计规则及下述存储规则。历史 `formal_sample=false` 不能升级。
2. **补真正的来源关联**：A/R 共用只读事件记录真实 engine 生成完成、评分返回与其执行 ID；R 另记 response/reward/tensor 原件复用及来源 ID。将故障前被杀批次的 32 条输入关联至恢复后的 `train_batch`、持久提交和最终加载。同 hash 的重新生成仍算重做；现有 `_compute_rewards` 入口事件不能冒充物理生成完成。来源无法判明则 `unverifiable`。
3. **复用现有 runner 与验收器**：只加 F2 固定 seed 成对入口及原始事件汇总，保留 fault→chain→input→load 链、每 run 超时和新证据目录。不建设通用六 cell 框架，不追加 F4/F1/X1/X2 正式矩阵、C/B 对照、184 项 CPU 大合同或 100 步多故障运行。改过的代码只跑对应的定向 CPU 测试。
4. **pilot 停跑**：1 对 F2＋1 对无故障须证明双方最终加载、R 原始输入来源与复用、A 的真实安全丢弃或复用分类，并测新版墙钟/磁盘。pilot 只验收机制和观测链是否可用，不按收益大小挑 seed。若 10 步 R 仍触及双方共同设定的运行上限，或来源证明失败，先解决具体问题再形成新冻结；不以旧 30 步门控通过为本窄实验的前置。

论文表必须同时给出保留中断工作与完整运行成本。若 R 复用工作但仍明显慢于 A，结论只能是“降低丢弃工作，代价是更高的运行成本”，不能写成总体效率优势。

## 6. 最小空间执行与证据保留

本节只适用于本方案的新 10 步 pilot 和正式 run，取代 FT-v1 修订 R1 对这些新 run 的保留规则。两臂使用同一**验收后**清理规则；训练中只允许各自已冻结实现本来的 checkpoint 行为，R 的运行中剪枝及其 I/O 仍计入完整 run 成本。不得为省空间关闭 A 的原生恢复、缩减 checkpoint 内容或频率，亦不得在独立加载验收前删分片。

1. **逐 run 串行**：一次只运行一个训练 run，随后完成 fault→chain→input→load 的适用验收、来源关联和成本汇总；新进程独立加载最终模型、optimizer、scheduler、RNG、数据游标并确认状态。无故障 run 走同版本的完整组、reward、状态加载验收。完成清理并复核可用空间后才启动下一个 run。固定 seed 的配对关系与顺序不变。
2. **永久保留的小证据**：冻结清单、源码/镜像/配置哈希、有效命令和 GPU UUID、故障与原生重试事件、执行来源 ID、32 条原始输入和评分的身份与必要原件、批次/提交链、完整验收报告、每个权重分片的路径/字节数/SHA-256、墙钟/GPU·小时、峰值磁盘、逐对结果及清理日志。原件若是重放证明必需的小文件，不能只留摘要哈希。
3. **大分片规则**：验收通过并完成独立加载的 pilot 全部删除该 run 的 DCP 权重 `*.distcp`；正式 F2 中，无论 A 是 `safe_discard` 还是 R 是 `correct_recovered`，只要安全且来源可判定，均在验收后删除大分片。无故障 run 同样在验收后删除。正式 F2 中预先按固定随机种子抽取 **1 个完整配对**，两臂都保留全量权重以及重新加载所需的 DCP metadata、`common.pt`、配置和路径映射；名单在正式运行前冻结，不能按结果挑选。删前流式计算哈希，删后核对实际释放量；保留所有小证据。删除后该 run 不能再次复验权重内容，论文需披露此限制。验收后哈希与清理的耗时和资源用量单独列账。
4. **失败与空间门槛**：`invalid_commit`、`safe_stop`、`timeout`、`technical_invalid`、`unverifiable` 或独立加载失败时停止后续 run，保留当前失败 run 的全量权重供诊断，不为凑空间而删掉失败原件；结果仍按预设规则登记。`P` 取 4 个新版 pilot 从启动至独立加载期间，在实际输出文件系统测得的**最大端到端空闲空间降幅**，包含重启残留和加载临时副本；正式每个 run 开始前要求该文件系统当时可用空间至少 `P + 20 GiB`，并确认所需四张 GPU 与输出目录。若 pilot 后更改实现或清理路径，重新测 `P` 并重新 freeze。磁盘不足即暂停，不覆盖或删其他 run 的未验收证据。

2026-09-24 清理旧 FT1 后 `/public` 约有 407 GiB 可用。旧 30 步 F2 门控的 R 磁盘峰值 34.7 GB（32.3 GiB），只能作初步容量参考，不能代替新版 10 步 pilot 的 `P`。本节通过串行验收后清理避免 26 个正式 run 的检查点累积；正式容量判断以新版 pilot 的 `P`、独立加载临时占用与每 run 前的现场空闲值为准。

## 7. 阶段 1 实施记录（2026-09-24）

已增加物理 `engine.agenerate` 返回事件、评分子进程返回事件，以及 A 样本执行 ID 在生成、批次和训练入口间的传递。新的来源验收器将 A 的执行 ID 或 R 的 response/reward/tensor 原件连接到最终保留状态；相同文本但不同请求仍判为重做。`generation_complete` 继续供旧故障调度使用，并明确标为评分入口观察，不作为物理生成证据。

已增加固定 seed 的 10 步 F2/无故障配对 pilot 入口。每次只运行一臂，在独立输入、状态链、最终状态加载及来源验收后，才对该 pilot 的 DCP 分片逐个记录 SHA-256 并清理。运行期间记录端到端磁盘峰值；每个 pilot run 启动前暂以 64 GiB 可用空间为门槛。正式 run 所需 `P + 20 GiB` 门槛仍须由四个新版 pilot 实测 `P` 后确定。

## 8. 阶段 2 停跑记录（2026-09-24）

已启动 F2 seed 419、A→R 的真实 pilot。首次 A 训练、故障与独立加载通过，但来源验收器误拒绝一次父进程已安全重试的评分；修订后 15 项定向 CPU 回归通过，旧 run 离线复验为 `safe_discard`，全量原件保留。用新目录重跑时，A 在恢复后的首次异步 DCP 保存发生 CUDA `invalid argument`，无最终状态，故按第 6 节规则停跑。R 和无故障 pilot 均未启动，正式样本仍为 0；四 run 的 `P` 尚未测得，正式 freeze 未成立。证据、源码差异、空间及下一步诊断门槛见 [阶段 2 停跑记录](STAGE2_PILOT_STOP_20260924.md)。

后续独立 A/F2 诊断在 DCP 之前的 backward 再次出现 `CUDA invalid argument`；v2 与诊断容器的内核日志均有同容器 NVIDIA 锁页路径的 order-9 分配失败。独立 GPU7 上 64 MiB、256 MiB、1 GiB pinned D2H 均通过，无法复现完整训练负载，尚无可信的最小代码修复。阶段 2 继续停跑；详细证据和下一步门槛已补入同一停跑记录。

再以 `CUDA_LAUNCH_BLOCKING=1` 在新独立目录定位，首次 DCP preload 的优化器 `exp_avg` 张量 D2H 报相同错误；同容器第三次出现 NVIDIA 锁页路径的 order-9 分配失败，故障注入尚未命中。该结果仍不足以将根因归于张量本身或提出安全的 DCP 代码修复。正式实验继续冻结在阶段 2，先完成节点/驱动侧诊断与修复验证。

## 9. 阶段 2 后续诊断与新版 pilot 完成（2026-09-24）

后续在固定镜像中确认 Inductor pointwise autotune 的 benchmark 会为被改写的约 622 MB GPU 张量创建 pinned CPU 备份；单核关闭 pointwise autotune 后仅产生一个 launcher，数值检查通过且无 host allocation。将该配置与同步 D2H 共同限定在最小实验入口，再用新目录、同四张 GPU、无诊断环境重跑。F2 seed 419 按 A→R、无故障 seed 421 按 R→A 串行完成四个真实 10 步 pilot；两对均 `pilot_pair_verified`，每 run 的独立完整加载、状态链和来源验收通过。F2 A 的目标来源为 0/32，R 为 32/32。四 run 的磁盘峰值最大 **P=34,727,661,568 B**，当前正式启动门槛 **P+20 GiB=56,202,498,048 B**；最终 `/public` 可用 **411,842,260,992 B**。验收后所有新版 pilot 的 DCP 分片均先哈希后删除；旧失败证据保留，正式样本仍为 0。此结果证明新版配置在四个 pilot 上可执行，不证明先前 CUDA 错误的唯一根因，也不构成性能比较结论。命令、冻结清单、各 run 验收/成本/空间与清理证据见 [阶段 2 完成记录](STAGE2_PILOT_COMPLETION_20260924.md)。
