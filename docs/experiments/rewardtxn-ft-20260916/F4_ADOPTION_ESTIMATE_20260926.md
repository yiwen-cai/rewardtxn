# F4' 离线复用率预估（2026-09-26，仅 CPU）

工具：`tests/ft/estimate_f4_adoption.py`。输入为阶段 2 门控的两次 R 无故障 run。结果：[JSON](F4_ADOPTION_ESTIMATE_20260926.json)。

**方法**
- 从首条样本入账到最后一次写盘收尾，每 0.5 s 设一个假想的 SIGKILL 时刻 t，共 968 个。
- 恢复 head：t 之前写盘已 finalize 的最新一代（lag-1 下会被提升）。V 取该代 `policy.json` 中的版本。
- 在途样本：t 之前已入账（以 `tensor.json` 的 mtime 近似）、且不在恢复链已消费集合中的 receipt。
- 可复用：满足 `TrainingBridge.authorize` 的条件，即每个 output version v 都满足 `0 ≤ V−v ≤ 2`。

| run | 在途已入账（中位） | 可复用（中位 / 均值） | 有任何可复用的切点占比 | 因版本领先被拒（中位） | 可复用占在途比例 |
|---|---:|---:|---:|---:|---:|
| s9225 | 96 | 96 / 87.0 | 99.8% | 0 | 98.9% |
| s6707 | 96 | 96 / 88.6 | 99.8% | 0 | 97.8% |

**结论**
- 审计担心的"版本领先导致采纳为 0"在实测时间线中基本不成立。
- 在途样本都是按 max_head_offpolicyness 用较旧权重生成的，恢复版本 V 通常不低于它们的版本。
- 任意时刻杀训练进程，R 预计能复用约 3 个批次（约 90 条）已入账的回答与评分。

**限制**
- 入账时间用 mtime 近似，略早于 `accept_result`。
- 假设恢复后的 `get_version()` 等于 `policy.json` 的版本。
- 未计入"切点处正在进行中、尚未入账"的样本，这部分两臂都会丢失。
- 这是离线推算，需要 GPU 试点验证。

**对 A 的含义（审计第 3 条）**：A 恢复时按数据加载器位置跳过已被取走的数据，这批在途样本对 A 来说是被丢弃的工作，而不是重新生成。因此在 F4' 下，两臂的 RTO 往往不可比，更贴切的主指标是"故障后被保留 / 被丢弃的已完成工作量"（与 F2 同类）。
